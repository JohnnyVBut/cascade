# Вход через 3x-ui: VLESS + Reality (self-steal)

> **Статус: черновик.** Схема собрана по документации и чтению кода Cascade, целиком на живом сервере
> не проверена. Список непроверенного в разделе 9. Вариант с обычным TLS и путём за Caddy:
> [DEPLOY_3XUI_TLS.md](DEPLOY_3XUI_TLS.md).

## 1. Что получится

```
Телефон (Happ)
   │  VLESS, проходит белые списки (БС)
   ▼
Сервер H1 Cloud: панель 3x-ui, inbound  →  outbound VLESS + Reality
   │  интернет, TCP 443, SNI = <DOMAIN>  (этот хоп под БС не находится)
   ▼
RU-хост ─ контейнер 3x-ui (Docker-сеть cascade-vpn, 172.30.0.2), inbound Reality (self-steal)
   ├─ клиент H1 (верный ключ + SNI)  → outbound direct
   │       │  Docker-сеть → хост, пересылка
   │       ▼
   │   Cascade (режим host): PBR, источник 172.30.0.0/24 → шлюз <GATEWAY>
   │       ▼
   │   AWG-шлюз → зарубежный сервер → интернет
   └─ любое другое подключение (браузер, сканер, чужой SNI, неверный ключ)
           → Caddy (dest): декой-сайт и админка Cascade
```

**Что сохраняется:**

| Функция | Как |
|---|---|
| Декой-сайт | отдаёт Caddy на 8444, посторонних Xray пересылает на него |
| Админка Cascade | `https://<DOMAIN>/<ADMIN_PATH>/` через Xray fallback → Caddy |
| Одноразовые ссылки `/cnf/*` | через Caddy |
| Панель 3x-ui | не публикуется, SSH-туннель (фаза 8) |

**Что меняется:** Caddy уходит с 443 на 8444 (фаза 7), исчезает HTTP/3 на внешнем 443 (декой-видео больше
не идёт по QUIC), в логах Caddy все клиенты будут с адреса контейнера. Админка зависит от контейнера
3x-ui: если он остановлен, внешний 443 недоступен вместе с админкой (остаётся SSH и `127.0.0.1:8888`).

**Ограничение: один адрес.** Для Cascade весь трафик через эту цепочку приходит с одного адреса
(`172.30.0.2`, а на зарубежной стороне, скорее всего, с адреса AWG-интерфейса RU-хоста). Различать
пользователей H1 здесь нельзя: политики Cascade (файрвол, PBR, NAT) применяются ко всей группе, лимиты
`tc` на пользователя недоступны. Пользователи и их квоты остаются в панели H1. Чтобы разделить группы,
делайте несколько контейнеров 3x-ui (по одному на группу) с отдельными IP и алиасами.

## 2. Исходные условия и значения

Предполагается: Cascade работает в режиме `host`, Caddy из `deploy/caddy` тоже в `host`, есть FQDN с
валидным сертификатом в `/etc/ssl/cascade/server.{crt,key}`, в Cascade есть шлюз (или группа) на
зарубежный сервер, на хосте установлен Docker, `net.ipv4.ip_forward = 1`.

| Обозначение | Значение |
|---|---|
| `<DOMAIN>` | ваш FQDN (он же SNI) |
| `<HOST_IP>` | публичный IP RU-хоста |
| `<GATEWAY>` | шлюз или группа шлюзов Cascade на зарубежный AWG |
| `<ADMIN_PATH>` | секретный путь админки из `deploy/caddy/.env` |
| `<N>` | fwmark PBR-правила (виден в Cascade после Apply) |
| Docker-сеть | `cascade-vpn`, `172.30.0.0/24`, шлюз `172.30.0.1` |
| Контейнер 3x-ui | `3xui`, IP `172.30.0.2` |
| Порт inbound (временный / итоговый) | `8443` / `443` |
| Порт Caddy после переноса | `8444` |

## 3. Порты

| Порт | Сейчас | Итог |
|---|---|---|
| 80 | Caddy | Caddy (ACME, редирект) |
| 443 | Caddy | контейнер 3x-ui (Xray, Reality) |
| 8444 | не занят | Caddy HTTPS, не снаружи |
| 8888 | Cascade, 127.0.0.1 | без изменений |
| 2053 | не занят | панель 3x-ui, **не публикуется** |

## 4. Пошаговая инструкция

Все команды выполняются на RU-хосте под root. Перед каждой фазой держите вторую SSH-сессию открытой.

### Фаза 1. Проверка исходного состояния (только чтение)

```bash
docker inspect cascade --format '{{.HostConfig.NetworkMode}}'
```
Ожидаем `host`.

```bash
ss -ltnup | grep -E ':(80|443|2053|8443|8444|8888)\b'
```
Ожидаем: 80 и 443 у Caddy, 8888 у Cascade на `127.0.0.1`, остальные порты свободны.

```bash
openssl x509 -in /etc/ssl/cascade/server.crt -noout -subject -ext subjectAltName -enddate
```
Ожидаем: имя `<DOMAIN>` в сертификате, срок в будущем.

```bash
docker network inspect $(docker network ls -q) --format '{{.Name}} {{range .IPAM.Config}}{{.Subnet}} {{end}}'
```
Ожидаем: подсеть `172.30.0.0/24` свободна (если нет, выберите другую и замените везде).

### Фаза 2. Docker-сеть и контейнер 3x-ui

```bash
docker network create --subnet 172.30.0.0/24 --gateway 172.30.0.1 cascade-vpn
```

```bash
mkdir -p /opt/3xui/db
```

Контейнер публикует только временный порт inbound (8443). Порт панели (2053) не публикуется. `NET_ADMIN`
не выдаётся: он нужен только fail2ban. Образ взят из README проекта; после проверки зафиксируйте тег.

```bash
docker run -d --name 3xui --restart unless-stopped --network cascade-vpn --ip 172.30.0.2 -v /opt/3xui/db:/etc/x-ui -e XUI_ENABLE_FAIL2BAN=false -p 8443:8443 ghcr.io/mhsanaei/3x-ui:latest
```

Проверка:

```bash
docker ps --filter name=3xui --format '{{.Names}} {{.Status}}'
```
Ожидаем `Up ...`.

```bash
curl -sI http://172.30.0.2:2053/ | head -3
```
Ожидаем ответ `HTTP/1.1 200` (или редирект).

```bash
docker exec -it 3xui x-ui setting -show
```
Покажет логин, пароль, порт и путь панели. **Сразу смените** логин, пароль, путь, включите 2FA.

Контейнер достучится до Caddy (так будет работать dest):

```bash
docker run --rm --network cascade-vpn busybox nc -zv -w 3 172.30.0.1 443
```
Ожидаем `open`. Таймаут означает, что файрвол хоста режет трафик из Docker-сети на сам хост: добавьте
разрешающее правило для подсети `172.30.0.0/24` (например, в ufw).

### Фаза 3. Политики в Cascade

Выполняется в интерфейсе Cascade. Цель: трафик подсети `172.30.0.0/24` уходит в шлюз `<GATEWAY>`, а
**ответы** на входящие соединения к контейнеру этим правилом не перехватываются.

Почему нужно два правила. Входящие соединения от H1 приходят на проброшенный порт, ответы идут от
`172.30.0.2` к H1. PBR с источником `172.30.0.0/24` пометил бы и их и отправил бы в AWG, соединение
оборвалось бы. Поэтому ответы выводятся из-под PBR правилом выше (первое совпавшее правило побеждает,
правило без шлюза останавливает разметку для совпавшего трафика).

1. **Aliases** → алиас типа `network`, имя `xui_net`, запись `172.30.0.0/24`.
2. **Firewall Rules** → правило **R0**: имя `xui-ingress-replies`, действие accept, интерфейс any,
   протокол tcp, источник `xui_net`, **порт источника `8443`**, назначение any, шлюз не указывать.
3. Правило **R1** (ниже R0): имя `xui-egress`, действие accept, интерфейс any, источник `xui_net`,
   назначение any, next hop `<GATEWAY>`. `fallbackToDefault`: **выключить**, если при падении шлюза трафик
   не должен уходить мимо зарубежного шлюза с RU-адресом (тогда будет blackhole); включить, если выход
   через RU разрешён.
4. Если политика по умолчанию Firewall **drop**, добавить разрешающее правило для входящих: tcp,
   назначение `xui_net`, порт назначения `8443`.
5. Убедиться, что R0 стоит **выше** R1, и нажать **Apply** (изменения применяются только по Apply).

Проверка:

```bash
iptables-nft -t mangle -S FIREWALL_MANGLE | head -20
```
Ожидаем: строка `-s 172.30.0.0/24 -p tcp --sport 8443 -j RETURN` стоит **перед** строкой
`-s 172.30.0.0/24 ... -j MARK --set-xmark ...`.

```bash
ip rule show | grep fwmark
```
Ожидаем строку с вашей меткой `<N>`. Значение видно в правиле R1 (UI или `GET /api/firewall/rules`,
поле `fwmark`).

```bash
ip route get 1.1.1.1 mark <N>
```
Ожидаем интерфейс AWG-шлюза, не основной интерфейс хоста.

### Фаза 4. Проверка выхода через шлюз (снаружи ничего не открыто)

```bash
docker run --rm --network cascade-vpn curlimages/curl -s -m 15 https://ifconfig.me
```
Ожидаем IP **зарубежного** сервера (сравните с `curl -s https://ifconfig.me` на зарубежном сервере).

| Результат | Причина и действия |
|---|---|
| IP самого RU-хоста | метка не применилась: нет Apply, R0 ниже R1, не тот fwmark; смотрите счётчики `iptables-nft -t mangle -L FIREWALL_MANGLE -v -n` (растёт ли `pkts` у MARK) |
| таймаут | зарубежная сторона не пропускает или не транслирует источник (ниже) |

**Проверить источник на зарубежной стороне.** Docker по умолчанию делает MASQUERADE для своей подсети на
любой исходящий интерфейс, кроме собственного моста, поэтому на AWG-интерфейсе источником, скорее всего,
будет адрес AWG-интерфейса RU-хоста. Проверить на RU-хосте во время теста выше:

```bash
tcpdump -ni <AWG_ИНТЕРФЕЙС_RU> -c 10 'not port 22'
```

Источник `172.30.0.2` означает, что подмены нет: на зарубежном сервере `AllowedIPs` пира должны включать
`172.30.0.0/24`, и в его Outbound NAT нужно правило MASQUERADE для источника `172.30.0.0/24`. Источник =
адрес RU-интерфейса: убедитесь, что для него на зарубежном сервере уже есть NAT (автоправила туннельных
интерфейсов).

### Фаза 5. Inbound Reality на временном порту 8443

В панели 3x-ui (SSH-туннель из фазы 8) создать inbound. Названия полей зависят от версии панели:

- протокол `vless`, порт `8443`, транспорт `tcp`;
- security `reality`; **Target (dest)** `172.30.0.1:443`; **SNI / Server Names** `<DOMAIN>`;
- сгенерировать пару ключей кнопкой в панели, задать short id (записать публичный ключ);
- uTLS fingerprint `chrome`;
- клиент: email `h1`, flow `xtls-rprx-vision`, UUID (сгенерируется панелью).

Outbound по умолчанию в 3x-ui `direct` (freedom). Не добавляйте метки и привязки к интерфейсам: выход ведёт
Cascade по сети.

Проверка fallback (посторонний заход отдаётся Caddy):

```bash
curl -sI --resolve <DOMAIN>:8443:127.0.0.1 https://<DOMAIN>:8443/
```
Ожидаем ответ декоя (HTTP 200) **без ошибок сертификата**.

Сквозная проверка с клиентского приложения (ПК или телефон, без БС): импортировать ссылку из панели
(кнопка у клиента) или собрать вручную:

```
vless://<UUID>@<HOST_IP>:8443?encryption=none&flow=xtls-rprx-vision&security=reality&sni=<DOMAIN>&fp=chrome&pbk=<PUBLIC_KEY>&sid=<SHORT_ID>&type=tcp#xui-reality
```
Ожидаем: сайт, показывающий IP, видит IP **зарубежного** сервера; счётчики клиента в панели растут.

### Фаза 6. Подключение H1

В панели 3x-ui на H1 **не меняйте** inbound, который проходит БС. Добавить:

1. **Outbound**: VLESS, адрес `<HOST_IP>`, порт `8443`, UUID и flow как в фазе 5, security reality,
   serverName `<DOMAIN>`, fingerprint `chrome`, publicKey и shortId из фазы 5.
2. **Правило маршрутизации**: нужный inbound (или пользователь) → этот outbound.
3. Применить настройки и перезапустить Xray из панели.

Проверка: телефон (сначала без БС, потом с БС) подключается к H1 и открывает сайт с IP. Ожидаем IP
зарубежного сервера. Если H1 не даёт менять outbound или маршрутизацию, схема на этом шаге останавливается.

### Фаза 7. Перевод на 443 (по желанию; затрагивает декой и админку)

Выполнять, если нужен именно порт 443. На этом шаге внешний 443 кратковременно недоступен.

0. Добавить в Cascade ещё одно правило R0 для порта источника `443` (как в фазе 3) и нажать Apply (и
   разрешающее правило для входящих на `443`, если политика по умолчанию drop).
1. Резервная копия и правка Caddyfile:

```bash
cp /root/cascade/deploy/caddy/Caddyfile /root/cascade/deploy/caddy/Caddyfile.bak
```

В `/root/cascade/deploy/caddy/Caddyfile` заменить адрес HTTPS-сайта:

```
-https://:443 {
+https://:8444 {
+    bind 127.0.0.1 172.30.0.1
     tls /certs/server.crt /certs/server.key
```

Caddy должен слушать адрес `172.30.0.1`, чтобы контейнер его видел (dest). Этот адрес существует только
при созданной Docker-сети (порядок запуска после перезагрузки: см. фазу 9).

2. Перезапустить Caddy:

```bash
docker restart cascade-caddy
```

3. Пересоздать контейнер с портом 443 (данные хранятся в `/opt/3xui/db`):

```bash
docker rm -f 3xui
```

```bash
docker run -d --name 3xui --restart unless-stopped --network cascade-vpn --ip 172.30.0.2 -v /opt/3xui/db:/etc/x-ui -e XUI_ENABLE_FAIL2BAN=false -p 443:443 ghcr.io/mhsanaei/3x-ui:latest
```

4. В панели изменить inbound: порт `443`, Target `172.30.0.1:8444`.
5. В панели H1 изменить порт outbound на `443`.

Проверка:

```bash
ss -ltnp | grep -E ':(443|8444)\b'
```
Ожидаем: 443 у `docker-proxy`, 8444 у Caddy на `127.0.0.1` и `172.30.0.1`.

```bash
curl -sI https://<DOMAIN>/
```
Ожидаем декой, валидный сертификат.

```bash
curl -sI https://<DOMAIN>/<ADMIN_PATH>/
```
Ожидаем ответ админки Cascade (редирект или страница), не 404 декоя.

### Фаза 8. Панель 3x-ui

Основной способ: SSH-туннель (панель наружу не публикуется):

```bash
ssh -L 2053:172.30.0.2:2053 root@<HOST_IP>
```

Затем `http://127.0.0.1:2053/` и путь панели.

Необязательно: открыть панель через Caddy под секретным путём (`handle /<XUI_PATH>/* { reverse_proxy
172.30.0.2:2053 }`, в панели задать тот же базовый путь, включить 2FA). Работа 3x-ui за префиксом пути не
проверялась; делайте это только вместе с 2FA и ограничением по IP.

### Фаза 9. Приёмка и перезагрузка

- [ ] `https://<DOMAIN>/` отдаёт декой, сертификат валиден, `http://<DOMAIN>/` редиректит на https.
- [ ] `https://<DOMAIN>/<ADMIN_PATH>/` открывает админку Cascade, API работает, `/cnf/*` работает.
- [ ] Панель 3x-ui открывается по SSH-туннелю.
- [ ] Телефон через H1 выходит с IP зарубежного сервера (вне БС и при БС).
- [ ] Отключение шлюза `<GATEWAY>` в Cascade даёт ожидаемое поведение (blackhole или переход на резерв).
- [ ] После `reboot` всё поднимается само: `docker ps`, `ss -ltnp`, оба `curl` выше.

Риск после перезагрузки (после фазы 7): если Caddy стартует раньше Docker-сети, он не сможет занять
`172.30.0.1`. Тогда `docker restart cascade-caddy`. Устойчивая альтернатива: слушать `0.0.0.0:8444` и
закрыть 8444 снаружи файрволом, разрешив только подсеть `172.30.0.0/24`.

## 5. Откат

После фазы 7 (возврат Caddy на 443):

```bash
docker rm -f 3xui
```

```bash
cp /root/cascade/deploy/caddy/Caddyfile.bak /root/cascade/deploy/caddy/Caddyfile
```

```bash
docker restart cascade-caddy
```

Затем при необходимости снова запустить контейнер из фазы 2 (с `-p 8443:8443`).

Фазы 2–6: остановить контейнер (`docker rm -f 3xui`), отключить правила R0 и R1 в Cascade и нажать Apply,
удалить сеть (`docker network rm cascade-vpn`).

## 6. Если что-то не работает

| Симптом | Вероятная причина |
|---|---|
| Выход с IP RU-хоста вместо зарубежного | PBR не применён: Apply, порядок R0/R1, метка |
| H1 подключается и сразу обрывается | ответы перехвачены PBR: нет R0 или неверный порт в нём |
| Нет интернета через цепочку | зарубежная сторона не транслирует источник или нет в AllowedIPs |
| Браузер видит ошибку сертификата на `<DOMAIN>` | Caddy отдаёт сертификат на другое имя; проверить `server.crt` |
| `https://<DOMAIN>/` не открывается после фазы 7 | Xray не может достучаться до Caddy: dest, bind `172.30.0.1`, файрвол |
| Админка 404 после фазы 7 | запрос пришёл на декой: проверить `<ADMIN_PATH>` и `.env` Caddy |
| Caddy не стартует после перезагрузки | см. риск в фазе 9 |

## 7. Сравнение с вариантом TLS

Этот вариант лучше скрывает прокси от активных проб и, вероятно, быстрее, но требует перенести Caddy с 443 и
делает админку зависимой от контейнера 3x-ui. Вариант «путь за Caddy» проще и не трогает 443, но путь
выдаёт Xray при попытке угадать. Подробно: [DEPLOY_3XUI_TLS.md](DEPLOY_3XUI_TLS.md).

## 8. Безопасность

- Токены и пароли панелей не записываются в репозиторий.
- 2FA на панелях, длинный случайный базовый путь, панель не публикуется.
- README 3x-ui оговаривает личное использование; обновляйте образ осознанно (фиксируйте тег).
- Условия H1 Cloud ограничивают рекламу как средства обхода блокировок и SNI-маскировку чужими доменами:
  проверьте, допускают ли они ретрансляцию на ваш сервер.

## 9. Что не проверено

- Схема целиком на вашем сервере.
- Что Reality в 3x-ui отдаёт посторонних клиентов локальному Caddy (проверяется `curl` в фазе 5).
- Что правило R0 (порт источника + `RETURN`) действительно отделяет ответы от PBR.
- Исходный адрес на зарубежной стороне при MASQUERADE Docker.
- Что панель H1 допускает собственный outbound и маршрутизацию.
- Что Caddy принимает несколько адресов в `bind`.
- Устойчивость к перезагрузке (порядок запуска Docker, Caddy, Cascade).

## 10. Версия образа

Образ `ghcr.io/mhsanaei/3x-ui:latest` не зафиксирован. После успешной проверки выполните
`docker inspect 3xui --format '{{.Image}}'` и замените `latest` в командах на конкретный тег или дайджест.
Пункты раздела 9 проверяются по ходу фаз 3–7.
