# Вход через 3x-ui: VLESS + TLS (путь за Caddy)

> **Статус: черновик.** Схема собрана по документации и чтению кода Cascade, целиком на живом сервере
> не проверена. Список непроверенного в разделе 9. Вариант с Reality (self-steal на 443):
> [DEPLOY_3XUI_REALITY.md](DEPLOY_3XUI_REALITY.md).

## 1. Что получится

```
Телефон (Happ)
   │  VLESS, проходит белые списки (БС)
   ▼
Сервер H1 Cloud: панель 3x-ui, inbound  →  outbound VLESS + TLS (WebSocket / XHTTP)
   │  интернет, TLS 443, путь /<SECRET_PATH>  (этот хоп под БС не находится)
   ▼
RU-хост ─ Caddy (443, ваш сертификат)
   ├─ /<SECRET_PATH>*  → reverse_proxy 172.30.0.2:10000  (контейнер 3x-ui, inbound VLESS без TLS)
   │       │  outbound direct, Docker-сеть → хост, пересылка
   │       ▼
   │   Cascade (режим host): PBR, источник 172.30.0.0/24 → шлюз <GATEWAY>
   │       ▼
   │   AWG-шлюз → зарубежный сервер → интернет
   ├─ /<ADMIN_PATH>/*  → Cascade (админка)
   ├─ /cnf/*           → Cascade (одноразовые ссылки)
   └─ остальное        → декой-сайт
```

TLS снимает Caddy со своим сертификатом, 443 остаётся у него. Порты контейнера наружу **не публикуются**:
Caddy на хосте обращается к контейнеру напрямую по `172.30.0.2`, поэтому DNAT нет и правило для ответов (R0 в
варианте Reality) не нужно.

**Что сохраняется (без изменений):**

| Функция | Как |
|---|---|
| Декой-сайт | Caddy, как сейчас |
| HTTP/3 (QUIC) на 443 | остаётся |
| Админка Cascade | `https://<DOMAIN>/<ADMIN_PATH>/`, как сейчас |
| Одноразовые ссылки `/cnf/*` | как сейчас |
| Работа админки при остановке контейнера 3x-ui | сохраняется |
| Панель 3x-ui | не публикуется, SSH-туннель (фаза 8) |

**Ограничение: один адрес.** Для Cascade весь трафик через эту цепочку приходит с одного адреса
(`172.30.0.2`, а на зарубежной стороне, скорее всего, с адреса AWG-интерфейса RU-хоста). Различать
пользователей H1 здесь нельзя: политики Cascade (файрвол, PBR, NAT) применяются ко всей группе, лимиты
`tc` на пользователя недоступны. Пользователи и их квоты остаются в панели H1. Чтобы разделить группы,
делайте несколько контейнеров 3x-ui (по одному на группу) с отдельными IP и алиасами.

**Слабое место варианта: секретный путь.**

Сервер отдаёт декой-сайт на любой адрес, кроме `/<SECRET_PATH>`. Если кто-то (сканер, проверяющая система)
запросит именно этот путь, он получит ответ Xray (например, ошибку 400 или 404 другого вида), а не декой. По
такому ответу видно, что на пути живёт не обычная страница, и сервер можно заподозрить в том, что он прокси.
Это и называется «путь угадан».

Насколько это серьёзно:

- Угадать длинный случайный путь перебором практически невозможно: 32 шестнадцатеричных символа
  (`openssl rand -hex 16`) это 128 бит случайности.
- Знание пути не даёт доступа: Xray проверяет UUID клиента. Утечка пути позволяет **обнаружить** прокси, но не
  пользоваться им.
- Сторонний наблюдатель по сети путь не видит: он передаётся внутри TLS.

Где путь может утечь:

- журнал Caddy `/logs/access.log` (путь пишется открытым текстом): ограничьте доступ к тому и журналу, не
  публикуйте его содержимое;
- ссылка или конфиг клиента (скриншот, пересылка в мессенджере в открытом виде);
- история браузера, если кто-то откроет этот адрес руками.

Что делать: длинный случайный путь, хранить его как пароль, не светить в логах и скриншотах. При подозрении
на утечку смените путь в inbound, в Caddyfile и в outbound на H1 и перезапустите Caddy.

Для сравнения: в варианте Reality пути нет вообще, любой посторонний всегда получает ответ настоящего сайта,
поэтому прокси так не обнаружить ([DEPLOY_3XUI_REALITY.md](DEPLOY_3XUI_REALITY.md)).

## 2. Исходные условия и значения

Предполагается: Cascade работает в режиме `host`, Caddy из `deploy/caddy` тоже в `host`, есть FQDN с
валидным сертификатом в `/etc/ssl/cascade/server.{crt,key}`, в Cascade есть шлюз (или группа) на
зарубежный сервер, на хосте установлен Docker, `net.ipv4.ip_forward = 1`.

| Обозначение | Значение |
|---|---|
| `<DOMAIN>` | ваш FQDN (он же SNI и Host) |
| `<HOST_IP>` | публичный IP RU-хоста |
| `<GATEWAY>` | шлюз или группа шлюзов Cascade на зарубежный AWG |
| `<ADMIN_PATH>` | секретный путь админки из `deploy/caddy/.env` |
| `<SECRET_PATH>` | новый длинный случайный путь (`openssl rand -hex 16`) |
| `<N>` | fwmark PBR-правила (виден в Cascade после Apply) |
| Docker-сеть | `cascade-vpn`, `172.30.0.0/24`, шлюз `172.30.0.1` |
| Контейнер 3x-ui | `3xui`, IP `172.30.0.2` |
| Порт inbound внутри контейнера | `10000` (не публикуется) |

## 3. Порты

| Порт | Сейчас | Итог |
|---|---|---|
| 80 | Caddy | Caddy |
| 443 | Caddy | Caddy |
| 8888 | Cascade, 127.0.0.1 | без изменений |
| 2053 | не занят | панель 3x-ui, **не публикуется** |
| 10000 | не занят | inbound внутри контейнера, **не публикуется** |

## 4. Пошаговая инструкция

Все команды выполняются на RU-хосте под root. Перед каждой фазой держите вторую SSH-сессию открытой.

### Фаза 1. Проверка исходного состояния (только чтение)

```bash
docker inspect cascade --format '{{.HostConfig.NetworkMode}}'
```
Ожидаем `host`.

```bash
ss -ltnup | grep -E ':(80|443|2053|8888|10000)\b'
```
Ожидаем: 80 и 443 у Caddy, 8888 у Cascade на `127.0.0.1`, остальные порты свободны.

```bash
openssl x509 -in /etc/ssl/cascade/server.crt -noout -subject -ext subjectAltName -enddate
```
Ожидаем: имя `<DOMAIN>` в сертификате, срок в будущем.

```bash
docker network inspect $(docker network ls -q) --format '{{.Name}} {{range .IPAM.Config}}{{.Subnet}} {{end}}'
```
Ожидаем: подсеть `172.30.0.0/24` свободна (если нет, выберите другую и замените везде).

### Фаза 2. Docker-сеть и контейнер 3x-ui

```bash
docker network create --subnet 172.30.0.0/24 --gateway 172.30.0.1 cascade-vpn
```

```bash
mkdir -p /opt/3xui/db
```

Порты не публикуются. `NET_ADMIN` не выдаётся: он нужен только fail2ban. Образ взят из README проекта;
после проверки зафиксируйте тег.

```bash
docker run -d --name 3xui --restart unless-stopped --network cascade-vpn --ip 172.30.0.2 -v /opt/3xui/db:/etc/x-ui -e XUI_ENABLE_FAIL2BAN=false ghcr.io/mhsanaei/3x-ui:latest
```

Проверка:

```bash
docker ps --filter name=3xui --format '{{.Names}} {{.Status}}'
```
Ожидаем `Up ...`.

```bash
curl -sI http://172.30.0.2:2053/ | head -3
```
Ожидаем ответ `HTTP/1.1 200` (или редирект).

```bash
docker exec -it 3xui x-ui setting -show
```
Покажет логин, пароль, порт и путь панели. **Сразу смените** логин, пароль, путь, включите 2FA.

### Фаза 3. Политики в Cascade

Выполняется в интерфейсе Cascade. Цель: трафик подсети `172.30.0.0/24` уходит в шлюз `<GATEWAY>`.

1. **Aliases** → алиас типа `network`, имя `xui_net`, запись `172.30.0.0/24`.
2. **Firewall Rules** → правило **R1**: имя `xui-egress`, действие accept, интерфейс any, источник `xui_net`,
   назначение any, next hop `<GATEWAY>`. `fallbackToDefault`: **выключить**, если при падении шлюза трафик
   не должен уходить мимо зарубежного шлюза с RU-адресом (тогда будет blackhole); включить, если выход
   через RU разрешён.
3. Нажать **Apply** (изменения применяются только по Apply).

Правило для ответов (R0) здесь не нужно: входящих соединений из интернета к контейнеру нет, Caddy
обращается к нему локально, и такие ответы доставляются локально, а не через PBR (проверяется в фазе 5).

Проверка:

```bash
iptables-nft -t mangle -S FIREWALL_MANGLE | head -20
```
Ожидаем строку с `-s 172.30.0.0/24 ... -j MARK --set-xmark ...`.

```bash
ip rule show | grep fwmark
```
Ожидаем строку с вашей меткой `<N>`. Значение видно в правиле R1 (UI или `GET /api/firewall/rules`,
поле `fwmark`).

```bash
ip route get 1.1.1.1 mark <N>
```
Ожидаем интерфейс AWG-шлюза, не основной интерфейс хоста.

### Фаза 4. Проверка выхода через шлюз (снаружи ничего не открыто)

```bash
docker run --rm --network cascade-vpn curlimages/curl -s -m 15 https://ifconfig.me
```
Ожидаем IP **зарубежного** сервера (сравните с `curl -s https://ifconfig.me` на зарубежном сервере).

| Результат | Причина и действия |
|---|---|
| IP самого RU-хоста | метка не применилась: нет Apply, не тот fwmark; смотрите счётчики `iptables-nft -t mangle -L FIREWALL_MANGLE -v -n` (растёт ли `pkts` у MARK) |
| таймаут | зарубежная сторона не пропускает или не транслирует источник (ниже) |

**Проверить источник на зарубежной стороне.** Docker по умолчанию делает MASQUERADE для своей подсети на
любой исходящий интерфейс, кроме собственного моста, поэтому на AWG-интерфейсе источником, скорее всего,
будет адрес AWG-интерфейса RU-хоста. Проверить на RU-хосте во время теста выше:

```bash
tcpdump -ni <AWG_ИНТЕРФЕЙС_RU> -c 10 'not port 22'
```

Источник `172.30.0.2` означает, что подмены нет: на зарубежном сервере `AllowedIPs` пира должны включать
`172.30.0.0/24`, и в его Outbound NAT нужно правило MASQUERADE для источника `172.30.0.0/24`. Источник =
адрес RU-интерфейса: убедитесь, что для него на зарубежном сервере уже есть NAT (автоправила туннельных
интерфейсов).

### Фаза 5. Inbound в 3x-ui (внутри контейнера)

В панели 3x-ui (SSH-туннель из фазы 8) создать inbound. Названия полей зависят от версии панели:

- протокол `vless`, порт `10000`, listen `0.0.0.0`;
- транспорт `ws` (WebSocket), путь `/<SECRET_PATH>`, **security none** (TLS снимает Caddy);
  вместо `ws` можно попробовать `xhttp` или `httpupgrade`, если их поддерживает панель H1 (проверить);
- клиент: email `h1`, UUID (flow не задавать: Vision здесь не применяется).

Outbound по умолчанию в 3x-ui `direct` (freedom). Не добавляйте метки и привязки к интерфейсам: выход ведёт
Cascade по сети.

Проверка с хоста (контейнер отвечает Caddy):

```bash
curl -sI http://172.30.0.2:10000/<SECRET_PATH>
```
Ожидаем ответ Xray (не страницу декоя; код может быть 400 или 404).

### Фаза 6. Блок в Caddyfile

Резервная копия:

```bash
cp /root/cascade/deploy/caddy/Caddyfile /root/cascade/deploy/caddy/Caddyfile.bak
```

В `/root/cascade/deploy/caddy/Caddyfile` в блок `https://:443 { ... }` добавить **выше** последнего блока
`handle { root * /srv/www ... }` (декой):

```
    handle /<SECRET_PATH>* {
        reverse_proxy 172.30.0.2:10000
    }
```

Перезапустить Caddy (admin API отключён, `reload` не сработает):

```bash
docker restart cascade-caddy
```

Проверка:

```bash
curl -sI https://<DOMAIN>/<SECRET_PATH>
```
Ожидаем ответ Xray (как в фазе 5), а не декой.

```bash
curl -sI https://<DOMAIN>/
```
Ожидаем декой, валидный сертификат.

```bash
curl -sI https://<DOMAIN>/<ADMIN_PATH>/
```
Ожидаем ответ админки Cascade.

Сквозная проверка с клиентского приложения (без БС):

```
vless://<UUID>@<DOMAIN>:443?encryption=none&security=tls&sni=<DOMAIN>&fp=chrome&type=ws&host=<DOMAIN>&path=%2F<SECRET_PATH>#xui-ws
```
Ожидаем IP зарубежного сервера, счётчики клиента в панели растут. Заодно проверьте, что соединение живёт
(страница с IP открывается повторно): это подтверждает, что ответы контейнера доставляются Caddy локально, а
не перехватываются PBR.

### Фаза 7. Подключение H1

В панели 3x-ui на H1 **не меняйте** inbound, который проходит БС. Добавить:

1. **Outbound**: VLESS, адрес `<DOMAIN>`, порт `443`, UUID как в фазе 5, security `tls`, serverName
   `<DOMAIN>`, fingerprint `chrome`, network `ws`, host `<DOMAIN>`, path `/<SECRET_PATH>`.
2. **Правило маршрутизации**: нужный inbound (или пользователь) → этот outbound.
3. Применить настройки и перезапустить Xray из панели.

Проверка: телефон (сначала без БС, потом с БС) подключается к H1 и открывает сайт с IP. Ожидаем IP
зарубежного сервера. Если H1 не даёт менять outbound, маршрутизацию или не поддерживает выбранный
транспорт, схема на этом шаге останавливается.

### Фаза 8. Панель 3x-ui

Основной способ: SSH-туннель (панель наружу не публикуется):

```bash
ssh -L 2053:172.30.0.2:2053 root@<HOST_IP>
```

Затем `http://127.0.0.1:2053/` и путь панели.

Необязательно: открыть панель через Caddy под секретным путём (`handle /<XUI_PATH>/* { reverse_proxy
172.30.0.2:2053 }`, в панели задать тот же базовый путь, включить 2FA). Работа 3x-ui за префиксом пути не
проверялась; делайте это только вместе с 2FA и ограничением по IP.

### Фаза 9. Приёмка и перезагрузка

- [ ] `https://<DOMAIN>/` отдаёт декой, сертификат валиден, `http://<DOMAIN>/` редиректит на https.
- [ ] `https://<DOMAIN>/<ADMIN_PATH>/` открывает админку Cascade, API работает, `/cnf/*` работает.
- [ ] Панель 3x-ui открывается по SSH-туннелю.
- [ ] Телефон через H1 выходит с IP зарубежного сервера (вне БС и при БС).
- [ ] Отключение шлюза `<GATEWAY>` в Cascade даёт ожидаемое поведение (blackhole или переход на резерв).
- [ ] Остановка контейнера 3x-ui (`docker stop 3xui`) не ломает декой и админку.
- [ ] После `reboot` всё поднимается само: `docker ps`, `ss -ltnp`, оба `curl` выше.

## 5. Откат

Вернуть Caddyfile и перезапустить Caddy:

```bash
cp /root/cascade/deploy/caddy/Caddyfile.bak /root/cascade/deploy/caddy/Caddyfile
```

```bash
docker restart cascade-caddy
```

Остановить контейнер (`docker rm -f 3xui`), отключить правило R1 в Cascade и нажать Apply, удалить сеть
(`docker network rm cascade-vpn`).

## 6. Если что-то не работает

| Симптом | Вероятная причина |
|---|---|
| Выход с IP RU-хоста вместо зарубежного | PBR не применён: Apply, метка |
| Нет интернета через цепочку | зарубежная сторона не транслирует источник или нет в AllowedIPs |
| Путь отдаёт декой | блок `handle /<SECRET_PATH>*` стоит ниже блока декоя или Caddy не перезапущен |
| Клиент не подключается по ws | не совпадают path, host или sni; панель H1 не поддерживает транспорт |
| Соединение рвётся через секунды | ответы контейнера перехвачены PBR: проверить, что Caddy обращается к контейнеру локально; при необходимости добавить правило без шлюза выше R1 для порта источника `10000` |
| Браузер видит ошибку сертификата на `<DOMAIN>` | Caddy отдаёт сертификат на другое имя; проверить `server.crt` |
| Админка 404 | запрос пришёл на декой: проверить `<ADMIN_PATH>` и `.env` Caddy |

## 7. Сравнение с вариантом Reality

Этот вариант проще и безопаснее для боевого сервера: порт 443, декой, HTTP/3 и админка остаются у Caddy,
порт контейнера не публикуется, правило для ответов не нужно. Минусы: путь выдаёт Xray при попытке угадать,
внутренний TLS внутри внешнего заметнее для анализа трафика, лишний хоп через Caddy, а истёкший
сертификат остановит и этот путь. Reality лучше скрывает прокси, но требует переноса Caddy с 443.
Подробно: [DEPLOY_3XUI_REALITY.md](DEPLOY_3XUI_REALITY.md).

## 8. Безопасность

- Токены и пароли панелей не записываются в репозиторий.
- 2FA на панелях, длинный случайный базовый путь, панель не публикуется.
- Секретный путь хранится как пароль: он виден в журнале Caddy.
- README 3x-ui оговаривает личное использование; обновляйте образ осознанно (фиксируйте тег).
- Условия H1 Cloud ограничивают рекламу как средства обхода блокировок и SNI-маскировку чужими доменами:
  проверьте, допускают ли они ретрансляцию на ваш сервер.

## 9. Что не проверено

- Схема целиком на вашем сервере.
- Что ответы контейнера к Caddy доставляются локально и не перехватываются PBR (проверяется в фазе 6).
- Исходный адрес на зарубежной стороне при MASQUERADE Docker.
- Что панель H1 допускает собственный outbound и маршрутизацию, и какие транспорты (ws, xhttp) она
  поддерживает; что для ws клиент предлагает ALPN `http/1.1`.
- Ответ Xray на запрос не по протоколу к пути ws (коды в фазе 5 приблизительные).
- Что работа через Caddy `reverse_proxy` без дополнительных настроек подходит для выбранного транспорта
  (для `xhttp` и gRPC могут потребоваться отдельные параметры прокси).
- Устойчивость к перезагрузке (порядок запуска Docker, Caddy, Cascade).

## 10. Версия образа

Образ `ghcr.io/mhsanaei/3x-ui:latest` не зафиксирован. После успешной проверки выполните
`docker inspect 3xui --format '{{.Image}}'` и замените `latest` в командах на конкретный тег или дайджест.
